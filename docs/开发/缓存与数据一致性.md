# 缓存与数据一致性

本文定义项目级可重建缓存的唯一实现和新增功能的接入规则。缓存不是用户文档、配置、
凭据、日志或可靠消息队列；这些数据不得为了“统一”而注册进缓存。

## 1. 组件与真相源

- `CacheRegistry`：声明资源 Schema、revision 算法、账号范围、类型、时效、离线策略、
  规范化、diff、依赖及写后失效。
- `CacheStore`：`cache.db` 的 SQLite WAL 存储；每线程短连接、事务提交、busy timeout，
  Linux 使用 `0700/0600` 权限。
- `CacheCoordinator`：两个生命周期托管 worker、优先级队列、single-flight、失败退避、
  身份 epoch fencing 和事件分发。
- `AuthSessionManager`：统一活动账号、`identity_epoch` 和远端 Session 互斥边界。
- 前端 `ResourceProvider`：内存直出、cache-only 首屏、SWR、job/event 轮询和受控应用新版。

`cache.db` 是运行时缓存唯一真相源。旧 CSV/JSON/头像只在一个兼容周期内惰性导入，
导入后立即标记待检查，不再双写。CSV 以后仅作为显式导出格式。

## 2. 首批资源

| resource | 时效 | 离线 | 依赖 | 说明 |
|---|---:|---:|---|---|
| `scores` | 5 分钟 | 是 | 无 | 页面、GPA、追踪共用 |
| `score-details` | 按需 | 是 | 课程指纹 | 按课程 variant 保存动态分项；不做历史全量扫描 |
| `academic-report` | 5 分钟 | 是 | `scores.revision` | 成绩真正变化才失效 |
| `research-training` | 5 分钟 | 是 | 无 | 目录、资格、确认课题；不含按需加载的联系方式和详情 |
| `festival-activities` | 30 分钟 | 是 | 无 | 仅自动模式保存四分区活动元数据与详情；证书导出实时重抓 |
| `avatar` | 24 小时 | 否 | 头像 token | BLOB；token 未变复用原图 |

收藏、GPA 模拟、追踪配置/state/outbox、Cookie、凭据、网站访问密码和日志不属于缓存。
评教、实验选课、考试与科研报名详情保持实时访问，但共享 Session 互斥和写后失效规则。

## 3. 时间与 revision 语义

- `revision`：规范化业务内容的版本化 SHA-256；远端排序和本地计算时间不得制造变化。
- `saved_at`：仅业务内容变化时更新。
- `last_checked_at`：远端成功检查后更新，即使内容不变。
- `last_attempt_at`：每次远端尝试更新。
- freshness 只根据 Registry 策略、`last_checked_at`、Schema 兼容和依赖 revision 判断。
- 文件 mtime 只可用于文件维护或用户文档列表，不得判断业务缓存新鲜度。

成绩稳定键是 `course_code + term`。名称、成绩、绩点、学分、状态等变化属于同课程修改；
缺少课程代码的异常旧数据使用确定性 fallback，不能互相覆盖。diff 必须覆盖新增、修改和
删除。

总成绩缓存额外保留不对浏览器公开的 `detail_ref`（远端 WID）。追踪比较和公开 diff 必须
排除该字段。`score-details` 的 variant 由成绩稳定键哈希得到，每次只查询一科；有效动态
分项才提交，空响应和失败均保留旧详情。详情 revision 不得触发成绩通知、培养计划失效或
GPA 基线协调。

## 4. 并发与认证边界

- single-flight 键：`(identity_epoch, account, resource, variant)`。
- 页面自动检查在 5 分钟内复用结果；失败后至少 60 秒再试；手动刷新绕过 freshness，
  但复用正在运行的同资源任务。
- 两个 worker 可并行处理本地工作；所有教务联网通过同一个 `remote_guard` 串行访问
  共享 `requests.Session`。
- 网络请求期间不持有 SQLite 事务或缓存锁。
- job 提交和最终提交都验证账号/epoch；最终验证与 SQLite commit 在同一 identity
  commit guard 内，防止 logout 后旧任务回写。
- 写操作不进入通用重试队列。成功后只发布失效并按需提交一次强制刷新。
- 每个远端写操作还必须登记到 `MUTATION_POLICIES`，明确
  `automatic_retry=False` 和失效视图；失败返回不得执行这些失效。
- 关闭服务时停止接单、取消排队任务，对运行任务有界等待；下一生命周期可重新启动。

锁顺序固定为：远端 Session 锁 → 身份状态锁 → 短 SQLite 事务。事件在数据库事务和
远端锁释放后分发；订阅者失败不能回滚缓存。SMTP 发送只能由追踪线程执行，不能阻塞
cache worker。

## 5. 页面和追踪协调

在线页面流程：

1. Provider 内存有数据则立即显示。
2. 浏览器刷新后调用 typed cache-only API 读取 SQLite，不检查远端会话。
3. 无缓存或超过资源时效时提交后台 job；离页不取消。
4. Provider 每 15 秒读取本地 cache events，不访问教务系统。
5. 留页发现新 revision 时提示“刷新当前显示/稍后”，并根据当前显示版本与后台版本生成
   变化摘要；首次无缓存完成后直接显示，不弹更新摘要。
6. 离页后只更新 Provider 的 available 数据，下次进入直接显示新版。

成绩追踪不再调用 `auth.academic` 或写 `scores.csv`。定时检查、立即检查、页面 SWR 和
登录预热共享 `scores` job；追踪订阅成绩事件，以 `last_notified_revision` 持久去重。
通知时间窗、初始通知、登录恢复和 outbox 仍由追踪服务管理。成绩变化后异步提交培养
计划刷新；失败保留旧报告，不撤销成绩或通知。

追踪首次建立基线时不查询详情；仅新增课程或最终成绩/绩点修改时，在通知前按需查询对应
课程。页面也只在用户点击成绩数字时提交单科详情 job，总成绩手动刷新不扩展为详情全量
刷新。

离线模式只读取 `offline_readable` 资源，不提交 job、不恢复认证、不发全局登录失效。
当前可离线打开成绩、培养计划、科研训练和自动模式保存的四节活动缓存；科研训练的详情、
刷新、收藏变更、报名与取消报名均保持禁用。四节活动离线只读元数据和已抓取详情，按需
读取、后台更新与证书打包保持禁用。

`festival-activities` 只在“自动读取并存储”模式使用 Registry。稳定键为分区和远端活动/
报名标识；规范化时稳定排序并移除证书 URL 临时时间戳和本地计算时间。按需模式不得读取
该条目、提交 refresh job 或提交缓存结果；其远端响应只返回当前请求。证书 archive 无论
模式都重新完整抓取四分区和详情，从当次快照筛选并下载，绝不依赖缓存 freshness 或证书
引用。

用户确认改为按需模式时，后端必须在当前身份 epoch 下精确删除
`CacheKey(current_account, "festival-activities", "default")`。禁止调用 `delete_account`、
通配资源或接受浏览器传入任意账号/resource/variant；删除成功后才允许前端保存按需偏好并
发起远端查询。存储异常、身份变化或删除未完成都必须返回失败，页面保留原模式并显示可
重试错误。删除成功需使离线能力和 Provider 状态失效，且测试必须证明其他账号、其他资源
及其他 variant 不受影响。删除还必须与相同 identity/account/resource/variant 的排队及
执行中 job 协调：精确取消并阻止提交，或等待完成后再删；成功响应后不得被旧 job 回写。
不得用账号级取消来规避这个竞态。

## 6. GPA 模拟是用户文档

GPA 文件不注册进 CacheRegistry。2.0 Schema 保存：

- `base_scores_revision`
- `base_report_revision`
- `base_real_scores`

模拟器发现培养计划基线 revision 变化时，升级确认弹窗同样展示新版变化摘要；旧文件未
保留完整培养计划时只能展示新版课程/学分概况，并明确无法逐门对比，不能把全量课程误报
为“新增”。
- 当前模拟课程

真实成绩变化时按 `course_code + term` 三方协调：未修改项自动升级；仅用户修改则保留；
双方修改逐课选择；新增真实课程选择加入；远端删除的课程保留并标注。培养计划的
`dependency_revisions.scores` 必须与模拟成绩基线一致，否则先协调成绩。旧 1.0 文件
按现有字段与当前真实数据建立一次基线，不修改原文件。

GPA 文档按账号哈希目录隔离并原子写入。旧文件只有存在可信 `exported_by` 时才复制到
账号目录；无 owner 的文件不能跨账号读取。

## 7. API 契约

typed cache 响应保留一个兼容周期的 `source / is_fresh / last_update`，同时返回：

```json
{
  "cache": {
    "schema_version": 1,
    "revision_algorithm_version": 1,
    "revision": "v1:...",
    "saved_at": "...",
    "last_checked_at": "...",
    "last_attempt_at": "...",
    "last_error_kind": null,
    "dependency_revisions": {},
    "is_stale": false
  }
}
```

通用接口：

- `POST /api/cache/refresh/{resource}`
- `GET /api/cache/jobs/{job_id}`
- `GET /api/cache/events?after={cursor}`

四节活动的“关闭自动存储”使用后端受控的 typed 删除操作，不扩展为可由前端任选资源的
通用删除接口。其鉴权、identity epoch fencing、精确 CacheKey 和事件语义与清理数据流程
一致，但删除范围仅为当前账号的 `festival-activities/default`。

resource 和 variant 必须受控；通用公开资源只支持 `default` variant，`score-details` 的
课程 variant 只能由 typed 成绩接口在后端生成。job/event 只允许当前
账号访问。事件接口不返回课程或个人 payload，首次调用只建立 cursor；事件每账号最多
保留最近 500 条，它不是可靠队列。

`throttled` 且没有 job ID 时会返回 `error_kind / retry_after_seconds`。前端必须结束首屏
loading 并给出可重试错误；job 的 `failed/cancelled` 不能当作手动刷新成功。

## 8. 新功能登记问题

实现新数据源前必须回答：

1. 数据属于缓存、用户状态、用户文档、可靠队列、安全状态还是日志？
2. account scope、variant、Schema、payload 类型和 canonicalization 是什么？
3. revision 覆盖哪些用户可见/业务字段？稳定键是什么？
4. freshness 与失败退避是多少？是否允许离线读取？
5. 依赖哪些资源，变化后影响谁？
6. 每个远端写成功后失效哪些资源？是否禁止自动重试？
7. 切号、logout、`clear_data` 如何处理？
8. 旧数据如何幂等迁移？Windows/Linux 升级是否保留？
9. Nuitka/Release 如何排除缓存与个人数据？

禁止页面、追踪器或新 router 自行新增文件 mtime、定时器或第二套缓存。现有规范不适合
新资源时，应修改 Registry/Coordinator 设计和本文，而不是绕开底层。
