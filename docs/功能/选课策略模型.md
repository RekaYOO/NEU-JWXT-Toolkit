# 选课策略模型

策略模型只用于 JWXK 的权重轮次（`selection_type_code = 04`）。它根据当前轮次市场数据、
用户方案组和官方剩余权重生成一套建议；生成建议本身不执行投权，应用建议仍需用户确认，
或由用户已经启动的后台策略任务执行。

抢选轮次（`02`）使用按意愿值排序的抢课/空位追踪状态机，不使用本模型，也没有“投权”
概念。完整工作台流程见[选课系统](选课系统.md)。

## 用户需要提供什么

- 方案组：每组包含候选课程和目标门数。
- 意愿值：每门课程 1–10 分，越高表示越重视。
- 年级人数：用于估计整个轮次的潜在需求，默认值为 5000，可按账号与学期保存。
- 是否允许时间未知课程：配置决定时间数据不完整的课程能否进入候选；已确认的硬时间冲突
  始终进入互斥约束。

预算、最低投权和步长来自官方接口，不允许前端自行扩大。课程容量与已投注人数在计算前从
当前轮次真实课程范围刷新；“全校课程查询”目录 `ALLKC` 不作为轮次市场样本或提交类型。

## 如何适配方案组

模型把方案组目标作为第一优先级：

1. 尽量满足更多方案组的目标门数。
2. 在目标满足程度相同时，最大化所选课程的意愿值总和。
3. 再比较中性情景下的代理效用。
4. 结果仍相同时，优先使用更少权重。

同一课程的多个教学班只消耗一门课程目标。教学班的实际选择由工作台保存的课程/班级信息
和提交链路处理，不会把同课多个班重复算入组目标。已经形成最终选课结果的课程参与目标和
冲突计算，但不再占用本次剩余权重。方案组之外的手动投权作为外部状态保留，自动任务不会
擅自撤回。

候选较少时使用确定性的组合搜索；达到节点数或时间上限时返回已经找到的最佳可行解，并在
结果中标记“近似”。无法满足全部目标时会返回每组缺少门数及预算、冲突、候选或数据警告，
而不是伪造完整方案。

## 实时分类与权重分配

当前实现把最新官方快照中“已投注人数严格小于容量”的课程归为 `SAFE`。`SAFE` 课程固定
使用官方最低投权，避免浪费权重；终局人数预测只作为风险参考。

其余被选入建议的课程归为 `COMP`，使用 water-filling 在剩余预算中分配整数权重。未进入
推荐组合的课程为 `OUT`，已经形成结果的课程为 `SELECTED`。

模型同时输出保守、中性和激进三个需求情景：

- 先根据完整轮次当前已投注次数、年级人数和预算估计平均参与课程数。
- 使用 `0.8 / 1.0 / 1.6` 三个系数生成情景需求。
- 按当前课程投注占比分配预测新增需求。
- 对 `COMP` 课程使用指数函数计算代理成功率。

这些数值是未校准的比较指标，不是真实录取概率，也不构成录取承诺。若市场范围与年级人数
明显不匹配，或三种情景退化为相同人数，界面会显示数据警告而不是假装预测可靠。

## 手动建议与后台策略

工作台可以即时生成一次建议，并显示：

- 推荐投权及当前投权；
- 当前已投注人数、容量和人数更新时间；
- `SAFE / COMP / OUT / SELECTED`；
- 三种情景的预测人数和代理值；
- 方案组完成情况、预算使用量、冲突和数据警告。

后台 `weight_strategy` 任务与方案组绑定。任务启动后可按配置间隔重算，或只在结束前窗口
执行。每次执行先刷新市场和候选数据；只有建议确实变化时才进入撤回、核验、重投流程。
写请求结果不明确时停止后续写操作并等待核验，绝不因会话恢复自动重放。

自动化间隔、结束前检查和邮件通知按账号与轮次保存在
`course_selection_automation_settings.json`；任务及最小核验状态保存在
`course_selection_tasks.json`。它们是用户配置和任务状态，不属于可淘汰缓存。

## 验证重点

- `backend/tests/test_course_weight_optimizer.py`：分组目标、冲突、分类、预算和近似搜索。
- `backend/tests/test_course_selection_api.py`：官方预算、市场数据、请求约束和手动策略接口。
- `backend/tests/test_jwxk_automation.py`：后台重算、撤回/重投核验、持久化和通知。
- 前端测试与生产构建：建议展示、参数边界、确认流程和移动端可达性。

测试不得对真实账号执行投权、撤回、选课或退课。
