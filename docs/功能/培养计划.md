# 培养计划

培养计划页对应 `/academic-report`，用于查看官方培养方案的类别层级、课程状态和学分缺口。
它不是简单按课程求和：类别要求、必修/选修口径、已通过成绩和当前已选课程会共同影响展示。

## 页面操作

- 左侧类别树（手机端为类别抽屉）选择培养计划层级。
- 搜索课程名称、代码、性质或学期，并按状态、学分、考核方式和成绩分制筛选。
- 课程行在桌面端整行可打开大纲；手机端从课程详情进入大纲。
- “学分统计”展示要求、已修、已选和剩余学分。
- 必修与选修缺口分组显示，不按缺口学分混排。
- 课程可从培养计划导入 GPA 模拟器；已经通过的课程不会作为待规划课程重复导入。

课程状态统一为：

- `passed`：成绩链路确认已通过；
- `selected`：当前选课/已投权链路确认已选择但尚未形成已通过成绩；
- `planned`：培养计划中存在、当前尚未通过或选择。

状态优先级为已通过高于已选。页面不会仅凭名称相似把课程认作同一门课；优先使用规范化
课程代码，并通过稳定指纹处理缺失代码的兼容数据。

## 学分计算

后端保留官方类别树，并为每个节点返回要求、已修、已选和剩余学分。计算遵循以下规则：

1. 已修学分来自已通过课程。
2. 已选学分来自当前选课结果和本轮已投权课程，但同一课程不得重复累计。
3. 课程先归入实际培养计划路径，再参与对应类别的必修或选修合计。
4. 父节点汇总子节点时遵守官方要求上限，避免同一课程跨层重复累计。
5. 同时包含总要求和子类别要求的通识选修等结构，分别展示总缺口和类别缺口；不能只用
   “通识选修”文本代替具体类别。

前端只展示后端规范化结果，不应在页面组件内重新实现一套学分算法。选课工作台的“培养
计划缺口”筛选复用相同类别路径和课程状态语义，但只负责定位目录课程，不改变培养计划。

## 大纲元数据

培养计划会按课程代码读取课程大纲模块允许持久化的最小元数据：考核方式、成绩分制、版本
和同步状态。页面可以后台同步缺失元数据，失败项可重试。完整大纲正文和附件不写入培养计划
缓存，详见[课程大纲](课程大纲.md)。

## 缓存与刷新

培养计划使用共享资源 `academic-report`：

- 打开页面先显示当前账号缓存；
- 默认时效为五分钟；
- 成绩资源 revision 变化会使培养计划失效；
- 刷新在后台完成，失败保留旧快照；
- 离线模式只读已有缓存。

培养计划依赖当前账号身份。账号切换、退出登录和缓存清理必须保持账号隔离。

## API 与实现

| 责任 | 位置 |
|---|---|
| 官方培养计划读取和规范化 | `backend/core/academic/report.py` |
| 缓存/刷新与摘要 API | `backend/app/routers/report.py` |
| 在线/离线展示模型 | `backend/app/presenters.py` |
| 页面与筛选 | `frontend/src/pages/AcademicReportPage.js` |
| 大纲联动 | `frontend/src/hooks/useCourseOutlineMetadata.js` |

主要接口：

- `GET /api/academic-report/cache`
- `GET /api/academic-report`
- `POST /api/academic-report/refresh`
- `GET /api/academic-report/summary`
- `GET /api/offline/academic-report`

## 排查学分差异

遇到“明明已选但仍显示缺学分”时，依次核对：

1. 课程代码是否与培养计划课程一致；
2. 当前记录是否属于同一账号与学期；
3. 选课记录是否是有效当前轮次记录，而非容量 `0/0` 的其他轮次记录；
4. 课程是否落入正确类别路径，尤其是通识选修子类别；
5. 成绩和培养计划资源的 revision 是否已经联动刷新。

不要用课程名称包含关系或页面显示文本临时补算。相关回归测试位于
`backend/tests/test_academic_report.py` 和 `backend/tests/test_mutation_invalidation.py`；新增前端
页面规则时应在 `frontend/src/` 下补充对应交互测试。
